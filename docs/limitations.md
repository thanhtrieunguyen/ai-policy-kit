# Known Limitations & Technical Boundaries

Transparency regarding architectural scope and design trade-offs is essential for maintainers adopting governance tooling. This document outlines the explicit technical and operational boundaries of **`ai-policy-kit`**.

---

## 1. Declarative Compliance vs. Forensic AI Detection

### The Boundary
`ai-policy-kit` is a **deterministic policy compliance engine**, not a forensic AI detection system. It verifies declared signals:
* Structured policy files (`ai-policy.yml`)
* Git commit trailers (`AI-Assisted: ...`)
* Pull request disclosure checkboxes (`- [x] Used AI assistant...`)
* Contributor accountability and DCO sign-offs
* Accidental assistant workspace directory leaks (`.cursor/`, `.claude/`, etc.)

If a contributor uses an AI coding assistant and intentionally conceals it—omitting commit trailers, skipping checklist items, and keeping local workspace files uncommitted—`ai-policy-kit` **cannot** detect that the code was generated by an AI.

### Architectural Rationale
This limitation is an intentional, foundational design decision:
1. **Statistical Unreliability**: Heuristic and statistical text/code classifiers exhibit high false-positive rates (20–40% on idiomatic code) and are easily defeated by basic formatting or variable renaming.
2. **Discrimination Against Non-Native Writers**: LLM detectors frequently flag straightforward, simple English prose written by non-native speakers as "machine generated."
3. **Flaky CI Pipelines**: Probabilistic scoring introduces non-reproducible CI failures, eroding developer trust.
4. **Precedent in Open-Source Governance**: Open-source communities have historically governed copyright, patents, and provenance through **declarative attestations** (such as the Linux Developer Certificate of Origin [DCO] and Apache Contributor License Agreements [CLA]), rather than automated surveillance.

## 2. Git Commit History Depth in CI

### The Boundary
To verify Git commit trailers across a pull request branch, `ai-policy lint-pr` inspects the range of commits between the base reference (`--base main`) and head reference (`--head HEAD`).

If your continuous integration pipeline performs a shallow clone (`fetch-depth: 1`), Git cannot traverse the commit history:

```yaml
# In GitHub Actions, ensure full history is fetched:
- uses: actions/checkout@v4
  with:
    fetch-depth: 0 # Mandated for commit trailer inspection
```

If shallow history is passed, `git log` may fail to locate intermediate commits or base revisions.

## 3. Platform-Specific PR Description Checklists

### The Boundary
`ai-policy lint-pr` parses Markdown task lists (`- [x] Disclosed AI usage`) provided via the `--pr-body` flag or GitHub Action payload.

* **GitHub**: Seamless integration via `${{ github.event.pull_request.body }}` in `action.yml`.
* **GitLab / Bitbucket / Gerrit**: While Git commit trailer verification works universally across all Git hosts, automated extraction of merge request description checklists on non-GitHub platforms requires passing the description text to the CLI explicitly via `--pr-body`.

---

## 4. Hermetic Zero-LLM Architecture

### The Boundary
`ai-policy-kit` has **zero external API dependencies**. It does not query OpenAI, Anthropic, Google, or any commercial AI detection SaaS.

### Benefits and Trade-offs
* **Benefits**:
  * **Zero Latency**: Executes locally in milliseconds.
  * **Complete Privacy**: Source code and commit logs never leave your local machine or CI runner.
  * **Zero Cost**: No API credits, rate limits, or recurring subscription fees.
  * **100% Offline**: Functions in air-gapped environments.
* **Trade-offs**:
  * Cannot provide semantic summaries or subjective analysis of code diffs.
  * Relies entirely on declarative rules and Git metadata.

## 5. Strict Schema Validation (`additionalProperties: false`)

### The Boundary
To protect repositories against subtle typos (e.g. typing `disclosures:` instead of `disclosure:`), the JSON Schema Draft-07 specification strictly enforces `additionalProperties: false` across all schema nodes.

If you add custom or unstandardized fields to `.github/ai-policy.yml`, validation will fail with:
```text
root: must NOT have additional properties: ["custom_field"]
```

Custom fields or experimental extensions must follow formal schema version releases or RFC proposals.
